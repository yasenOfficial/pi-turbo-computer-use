# Disposable Brave desktop-isolation results (2026-10-07)

Run `tests/test-brave-desktop-isolation.sh`; optional **test-only** variations: `PI_BRAVE_A11Y_MODE=bridge`, `PI_BRAVE_FORCE_A11Y=1`, `PI_BRAVE_BROWSER_GTK_MODULES=0`, and `PI_BRAVE_CASE=0|1|2|3|4|5`. `DAEMON_BIN` selects an already-built daemon (default `daemon/target/release/pi-turbo-daemon`). `PI_BRAVE_KEEP_LOGS=1` retains the disposable logs. Exit 77 means isolation prerequisites are unavailable; it never falls back to a networked browser. Bubblewrap supplies private network/PID namespaces and `/tmp`; the runner uses private HOME/XDG/profile, `dbus-run-session`, Xephyr, Metacity, a 0600 daemon socket, local HTML and a fixture-only `.desktop` ID. Only Xephyr uses the explicitly bound host X socket. No real user profile, browser window, desktop settings or network accounts are used. The browser's `--disable-setuid-sandbox` is **test-only** for namespace compatibility; no production browser arguments are changed. Installed Brave was 154.1.96.61. The GIO fixture launches the installed wrapper with the **same disposable profile** and another `--new-window` request.

## Before the accessibility proxy fix (old release binary)

The plain matrix and force-renderer-accessibility **without** bridge activation both exited 0, but the Brave web AT-SPI tree was absent: 19 nodes, no Brave app or page controls. Those were **not** primary-crash passes. With a private AT-SPI bridge, `PI_BRAVE_FORCE_A11Y=1` and `PI_BRAVE_BROWSER_GTK_MODULES=0`, the standalone no-daemon bridge control retained its Brave window/process and emitted owned-title accessibility events. A separate GTK input/button probe registered on the private accessibility bus. Daemon observation then returned a Brave app (71 snapshot nodes) but Brave subsequently **aborted**: original XID vanished, profile-specific PID exited, and Brave stderr contained three `GLib-GObject: g_value_type_compatible: assertion 'src_type' failed` lines followed by `dbus[…]: Array or variant type requires that type variant be written, but end_dict_entry was written. The overall signature expected here was 'a{sv}'` and `Aborted (core dumped)`. The installed Brave wrapper misleadingly returned exit 0. In the full old-release run, focus cases lost their windows *before* the focus request could find them. Reproduced independently in case 2 with private GTK controls verified before Brave launched. No particular AT-SPI call was proven causal from those logs alone.

## After parent-built release with disabled zbus proxy property caches

`PI_BRAVE_A11Y_MODE=bridge PI_BRAVE_FORCE_A11Y=1 PI_BRAVE_BROWSER_GTK_MODULES=0 tests/test-brave-desktop-isolation.sh` now exits **0** across all six cases (including extra case 0 with bridge/GTK probe/event monitor but **no daemon**). Cases 2–5 each start with a **Brave application, 306 snapshot nodes, an `entry` named `Pi Brave isolation input`, and a `push button` named `Pi Brave isolation action`** under the unique disposable page title; both page controls remain exposed in seven repeated observations. The separate GTK probe's *two* controls are independently confirmed via the private AT-SPI registry before Brave starts (`GTK_PRIVATE_REGISTRY_OK`). The daemon snapshot does not necessarily include that separate GTK utility window; the independent registry check is the GTK positive control. All original XIDs remain mapped/normal and profile-matched Brave PIDs remain present; no abort was logged. Cases 3 and 4 receive focus acknowledgement **and** Xephyr's actual `_NET_ACTIVE_WINDOW` equals the unique owned XID, including the composited overlay + activity-lease case. Case 5 receives a fixture GIO launch acknowledgement **and** gains a second owned EWMH XID while retaining the first. An acknowledgement alone is not treated as execution.

A separate private-bus `dbus-monitor` helper counts `org.freedesktop.DBus.Properties` method calls **from the daemon's PID only** (sender PID checked through the same private bus): case 2 **2,942 Get / 0 GetAll**; case 3 **1,260 / 0**; case 4 **1,260 / 0**; case 5 **1,653 / 0**. This is runtime counter-evidence against the old implicit `GetAll` path *in this isolated run*, consistent with the parent's disabled-cache fix; it is not proof that no other environmental factor can cause a Brave crash. In the last run, initial observations took **104–127 ms**, case-2 semantic action/readback **434 ms**, case-3/4 focus plus active-XID verification **3/6 ms**, native GIO acknowledgement **3 ms**, and second EWMH window appearance **849 ms**. Full individual cases lasted approximately **6–8 seconds** under these conditions; timings are samples, not guarantees.

**Semantic action scope/limit:** case 2 revalidates the unique XID, exact owned title in the entry/button ancestor chain and their roles immediately before each action. Brave returned `UnknownMethod` for AT-SPI `EditableText.SetTextContents` on its HTML entry: **Unicode node-ID `set_text` did not work** and is reported as such (`unicode_value: false`, with the IPC error). This is a separate unsupported Brave method, not evidence of a failed browser-crash fix. The test then clicks that same uniquely owned entry, confirms semantic focus and actual Xephyr focus, types an ASCII fixture string through IPC `set_text` **without** an ID, and verifies its value through the owned AT-SPI entry. It clicks the uniquely owned local-only button via node ID and confirms `Pi Brave clicked ✓` appears in the AT-SPI graph. No unsupported Unicode success is claimed; no input targets an arbitrary or real-user window.

**Without `--force-renderer-accessibility`**, `PI_BRAVE_A11Y_MODE=bridge PI_BRAVE_BROWSER_GTK_MODULES=0 tests/test-brave-desktop-isolation.sh` also exits **0** and all windows/processes survive focus, overlay and native GIO launch, with a Brave application node and observed private `Get` calls (31/62/62/62; `GetAll=0`). However the local **web input/button do not appear** (21 nodes). The no-force run is therefore a window-liveness comparison only, **not** a web-semantic/crash-path validation. Forced renderer accessibility was explicitly scoped to the successful web-controls variation and was **not** silently added to production. These results demonstrate this disposable environment, not a guarantee of seamless real-user-browser behavior.
